# Beta pública de Caramelo — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. No delegar sin una elección explícita del usuario.

**Goal:** Preparar una beta compartible con costos acotados, sesiones recuperables y pruebas reproducibles.

**Architecture:** Un proceso Node y SQLite en volumen persistente. HTTPS en proxy conocido, origen fijo y límites antes de llamar a proveedores. Publicación como paso separado tras revisar costo y destino.

**Tech Stack:** Node.js >=22.9, SQLite, node:test, Playwright y workflow GitHub existente.

**Spec:** [Diseño aprobado, sección C](../specs/2026-09-20-caramelo-design.md).

## Global Constraints

- Claves solo en servidor; no guardar ni publicar mensajes de jugadores por defecto.
- Tests deterministas sin red; evaluación real separada con presupuesto explícito.
- No publicar, desplegar ni contratar servicios con esta tarea de planificación.
- Móvil primero: 320 px como ancho mínimo; entrada de 16 px y objetivos táctiles de 44 px.

### Task 1: almacenamiento y recuperación

**Interfaces:** `createSqliteStore({filename,now}) -> Store`, compatible con Store
del plan 01, más `close()` y `purgeExpired()`. `now` inyectable para tests de TTL.

- [ ] Seleccionar dependencia SQLite usando documentación oficial y comprobar
  compatibilidad Node>=22.9; fijar versión y generar lockfile. No elevar requisito
  de Node solo para usar una API experimental sin necesidad.
- [ ] Escribir regresión de persistencia con directorio temporal de tests:

```js
test('persiste la respuesta idempotente tras reabrir',()=>{
 const first=createSqliteStore({filename,now:()=>1000});
 first.createGame(game);
 first.begin(request);
 first.commit(request.turnId,nextGame,response);
 first.close();
 const second=createSqliteStore({filename,now:()=>1001});
 assert.deepEqual(second.begin(request),{kind:'cached',response});
 second.close();
});
```

`createGame(game)` se agrega también a MemoryStore del plan 01. Fixture game usa
spec A, request UUID y expectedVersion0; nextGame version1; response omite historial.

- [ ] Crear esquema inicial:

```sql
CREATE TABLE games(id TEXT PRIMARY KEY, version INTEGER NOT NULL,
  state TEXT NOT NULL, expires_at INTEGER NOT NULL);
CREATE TABLE turns(game_id TEXT NOT NULL, id TEXT NOT NULL, payload_hash TEXT NOT NULL,
  status TEXT NOT NULL, evaluation TEXT, response TEXT, lease_until INTEGER,
  PRIMARY KEY(game_id,id));
CREATE TABLE budgets(day TEXT PRIMARY KEY, reserved INTEGER NOT NULL DEFAULT 0,
  spent INTEGER NOT NULL DEFAULT 0);
CREATE TABLE limits(bucket TEXT PRIMARY KEY, count INTEGER NOT NULL, expires_at INTEGER NOT NULL);
```

- [ ] `begin` usa transacción corta para verificar payload/version y reservar lease.
  `commit` compara versión e inserta resultado y estado en una sola transacción.
  Lease inicial 30 s; una operación expirada se marca failed y conserva evaluación.
  Nunca mantener la transacción mientras espera al proveedor. TTL elimina game y
  turns a la hora; purga al iniciar y periódicamente. Desactivar backups históricos
  de datos de sesión o aplicar el mismo TTL a sus copias.
- [ ] Probar conflicto de versión, doble begin concurrente, expiración y reapertura.
  Agregar `data/` y archivos SQLite de runtime al ignore; fixture sintético no
  contiene claves. `node --test test/persistence.test.mjs`; commit de esta tarea.

### Task 2: origen público, límites y presupuesto

**Interfaces:** `readDeploymentConfig(env)` retorna modo local/public y valores
validados. `reserveBudget({day,maxCost,limit}) -> reservationId`;
`settleBudget(id,actualCost)` devuelve reserva sobrante. Costos en enteros de
microunidades monetarias; sin floats para el ledger. En llamada de resultado
desconocido conservar reserva conservadora hasta conciliación.

- [ ] Test fallido de configuración incompleta:

```js
test('modo público no arranca sin presupuesto y origen HTTPS',()=>{
 assert.throws(()=>readDeploymentConfig({CARAMELO_MODE:'public'}));
 assert.throws(()=>readDeploymentConfig({CARAMELO_MODE:'public',
   PUBLIC_ORIGIN:'http://example.com',DAILY_BUDGET_MICROS:'1000000'}));
});
```

- [ ] Configurar variables `CARAMELO_MODE`, `PUBLIC_ORIGIN`, `DAILY_BUDGET_MICROS`,
  tarifas por modelo y `TRUSTED_PROXY_IPS`. Modo local conserva 127.0.0.1. Modo
  público requiere HTTPS/origen exacto, tarifas válidas y secreto de sesión si el
  mecanismo elegido lo necesita. No imprimir config con claves en errores.
- [ ] Host/origen permitidos derivan solo de PUBLIC_ORIGIN configurado; cookies
  públicas Secure/HttpOnly/SameSite. IP de cliente solo desde proxy explícitamente
  confiado; sin confianza, usar socket. Limitar 10 partidas/IP/h y 12 solicitudes
  de turno/sesión/min. Responder 429 + Retry-After antes de llamar modelos.
- [ ] Reservar costo máximo antes de cada llamada del pipeline usando tokens de
  entrada conocidos y máximo de salida. Sumar intentos y validaciones Jev, no solo
  redacción. Si no hay saldo, 429/503 recuperable sin consumir turno. No reiniciar
  presupuestos al reiniciar proceso.
- [ ] Probar carreras: dos reservas que exceden juntas el límite no pueden ambas
  aprobarse; replay no llama proveedores; errores facturables cuentan; IP spoofing
  no evita límite. Ejecutar tests de budget, config y servidor; commit.

### Task 3: observabilidad, CI y revisión de salida

**Interfaces:** métrica `{event,provider,model,latencyMs,inputTokens,outputTokens,
costMicros,status}`; prohibidos message/history/line/key/Authorization/cookie.

- [ ] Implementar whitelist de métricas:

```js
const fields=['event','provider','model','latencyMs','inputTokens',
 'outputTokens','costMicros','status'];
export function safeMetric(input) {
 return Object.fromEntries(fields.filter(key=>Object.hasOwn(input,key))
   .map(key=>[key,input[key]]));
}
```

Validar además tipos y valores enum de event/status; no permitir error.message
arbitrario en status. Test con credenciales/texto ficticios comprueba su ausencia.

- [ ] Agregar aviso corto en UI sobre envío de mensajes a los proveedores
  efectivamente elegidos. Mostrar limitación por presupuesto sin revelar claves,
  prompts ni respuestas crudas. No almacenar conversaciones en telemetría.
- [ ] CI instala versión Node compatible, `npm ci`, `npm test`, navegador de
  Playwright y E2E con proveedores simulados. Mantener escaneo de secretos y
  permisos read-only. Ninguna clave real en CI; acciones fijadas a SHA verificado.
- [ ] `docs/beta-runbook.md` debe contener comandos locales, env necesaria sin
  valores reales, backup/TTL, comprobación de salud, restauración de versión
  anterior, corte de presupuesto y procedimiento de rotación de claves.
- [ ] Antes de publicar, inspeccionar historial de commits, archivos servidos y
  bundle; probar que `.env`/SQLite y rutas arbitrarias no se sirven. No confundir
  aprobación del scanner con garantía de ausencia de todo secreto.
- [ ] Ejecutar matriz E2E: win/loss, doble envío, timeout recuperable, reinicio
  del servidor, TTL, presupuesto agotado, final omitido, reduced motion y móvil.
  Pedir pruebas físicas Safari/iPhone y Chrome/Android al usuario cuando no haya
  dispositivo disponible. Registrar pendientes honestamente.
- [ ] Preparar ficha de despliegue: proveedor concreto, región, dominio, costo
  estimado, volumen y límite diario elegido. Solicitar aprobación solo sobre esa
  ficha concreta; no desplegar, cambiar DNS ni contratar automáticamente.
- [ ] Commit final de preparación; entregar reporte con checks ejecutados,
  métricas reales de conversación y verificaciones humanas aún pendientes.
